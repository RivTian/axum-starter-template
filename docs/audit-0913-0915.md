# 备份分支取证审计：`backup/main-20260913` 与 `backup/main-20260915`

> 阶段：Phase 0（取证审计，无门禁）。
> 本文是**缺陷台账**，不是设计文档，也不是改造计划。它的唯一用途是：让 Phase 1 的每一条设计决策都能指向一份既有证据，而不是指向一句"细节没处理好"。

---

## 结论摘要

1. **两个分支都不是可增量修补的基线，但失败方式完全不同。**
   - A（0913）的失败集中在**纪律没有落点**：大量正确的推理写在注释与 README 里，缺少让违例变红的机制；以及**静默失败面**：跳过即通过、回落即沉默、未登记即"已生效"。
   - B（0915）的失败集中在**门禁自身的可信度**：真实进程门禁做得极好，但"已验证清单"是人工列表、渲染白名单是一层 glob、未交付文档检查是硬编码正则；以及**锚点与遥测顺序**这两处启动期语义错误。
2. **两个分支在同一处纪律上各对了一半**，新设计必须同时取两边：
   - 路径锚点：A 的 `core/src/util/paths.rs` 是任务书 §5.9 的正解，B 用的是 cwd（B-09）。
   - 渲染面：B 的 `include` 白名单 + `package =` 别名是正解（0 个 `.rs` 含 `{{`），A 是黑名单 + 36 个 `.rs` 含 `{{`（X-11）。
   - 停机预算：B 的 `Budgets::plan` 累积绝对边界是正解，A 是每层各拿一份同名时长（A-02、A-11）。
   - 冷段判别：B 的类型全等 + 穷尽解构（编译期红）是正解，A 的前缀白名单默认判"已生效"（A-29）。
3. **共 84 条缺陷条目**（A 34 条 / B 38 条 / 跨分支与文档↔实现 12 条），六类齐全，每条都指到具体文件。
4. **§7 的 13 个决策点全部有既有证据**，没有一条需要标注"无既有证据"；其中 DP13 的四个子项（CORS / OpenAPI / Prometheus / HTTP 客户端）两分支均无实现，按"证据为空即拒绝准入"处理，理由见 §7。

## 2. 缺陷类别定义

| 类别 | 判据 |
| --- | --- |
| **语义错误** | 代码在某个可达输入下产生与其自身声明不符的结果。与"风格"无关。 |
| **纪律无落点** | 存在一条明确的纪律（注释、README、设计文档），但没有任何机制会在违反时变红。 |
| **纪律有落点但无证据** | 有测试/门禁，但该测试在结构上无法发现它声称守护的违例（代理断言、人工清单、接受多种结果）。 |
| **静默失败面** | 失败路径以"成功"的外观收场：跳过即通过、解析失败即回落、未登记即判"已生效"。 |
| **工程链缺陷** | 模板生成链、门禁编排、工具链固定或交付边界上的缺陷，不涉及运行期语义。 |
| **文档与实现不符** | 文档（含注释）与代码对同一件事给出互相矛盾的陈述。 |

## 9. 对新设计的硬约束汇总

以下 18 条由本台账直接导出，Phase 1 的 `docs/architecture.md` 必须逐条给出落点与证据，不得只在正文里复述。

1. **凡是 release 里会消失的检查（`debug_assert!`）一律不作为纪律载体**；唯一性、不变量必须是运行期错误。（A-01、X-03）
2. **关停总时长必须有上界**，abort 之后的 join 是独立的第二段预算；预算以**一个绝对 deadline** 沿关停链传递，不是每层各拿一份同名时长。（A-02、A-11、B 的 `Budgets::plan`）
3. **收割函数必须返回结论**（是否被迫强杀 + 哪些任务没收回来），由调用方决定退出码；日志结论行必须反映真实结果。（A-03、A-11）
4. **编排层自己必须遵守它对各面提出的 `biased` 纪律**；依赖 `select!` 分支顺序的正确性必须有一个能在顺序被改后变红的用例。（A-04、B-37）
5. **关停期间的第二个信号 = 立即强制退出**，且该路径有测试。（A-05）
6. **任何 `cfg` 分支都必须有一条门禁编译它**，否则不写。（A-07、B-15）
7. **"等待某段代码就位"的信标必须由那段代码本身发出**；顺序不变量用顺序证据钉，不用基数代理；黑盒断言指向被断言值的真实来源。（A-08、A-09、A-16）
8. **任何"解析失败/取不到 → 回落缺省"的分支都必须留痕**；已识别选项的参数缺失必须 fail-fast。（A-10、A-12、B-05、B-07）
9. **顶层任务的 future 输出类型必须能承载失败**；任务名必须是常量或枚举，禁止字面量比较；运行时归属从 `Handle` 派生，不接受调用方自述。（A-14、B-01、B-02、B-14）
10. **"必须用包装提取器"必须由 lint 配置或类型落地**；`allow` 只打在最小单元上；没有消费者的语义变体、上限常量、映射与测试一律不预铺。（A-15、A-18、B-08、B-19）
11. **门面的"不泄漏"必须同时覆盖成功类型与错误类型**；单后端最小编译闭包 + 一条"二进制里只有一个后端"的门禁；诊断路径的超时预算不得比主路径更松。（A-17、A-19、X-12）
12. **环境门控的测试不能以 pass 收场**；"没跑"必须与"跑过且绿"在结果面上可区分；门禁不得接受两种结果；"已验证清单"由断言执行本身生成。（A-20、A-21、A-22、B-11、B-12）
13. **冷/热是配置类型自身的属性**，由穷尽解构或类型分区保证"不登记就编译不过"；"报告"与"回滚"由同一份事实推导，不允许两份人工清单；watch 里的值恒等于在效值。（A-28、A-29、X-08、B-17）
14. **配置写入端只在装配层且只在启动路径**；reload 路径只读，文件缺失 = 重载失败 + 保留 last-good；全进程只有一个路径锚点 = 可执行文件所在目录。（X-07、B-09）
15. **遥测初始化早于任何可能失败的启动步骤**；ANSI 由 `is_terminal()` 决定并有"非 TTY 输出不含 `\x1b`"的门禁；日志格式被下游解析即为公开接口，需要快照测试。（B-06、X-06、B-35）
16. **渲染面用白名单且不含 `.rs`**；项目名靠根 manifest 的 `package =` 别名挡在 Rust 源之外；未展开占位符终检匹配通用 `{{ … }}` 形态；反向映射按已知成员名集合逐项替换；名字矩阵必须含带连字符的前缀；至少一条门禁走用户真实的 `--git` 安装路径。（X-11、A-31、A-33、B-22、B-25、B-26）
17. **门禁的输入目录必须是模板的精确投影**（增量只允许发生在 `target/`）；工具链版本固定（`rust-toolchain.toml`）否则格式类门禁不可复现；生成结果只保留**一个**门禁入口 `make check`；后置钩子每一步都校验结果并在失败时中止。（A-32、X-05、X-09、B-27、B-28）
18. **文档只陈述能被门禁反向生成的能力**；验证记录每一行自带"本次/沿用"标记；crate README 的目录树若保留就必须有门禁比对；随交付物发布的文件一律使用交付语言。（B-20、X-10、A-34、B-32、B-34）
