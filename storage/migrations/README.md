# 迁移

`sqlx::migrate!("./migrations")` 在**编译期**把这个目录整个读进二进制。运行期不会再来读磁盘——
所以部署产物里没有这个目录也能正常迁移，反过来，改了这个目录而没重新编译则等于没改。

## `../build.rs` 不可删

cargo 默认只盯着 `.rs` 文件。没有 `build.rs` 里那行 `cargo::rerun-if-changed=migrations`，
改这个目录**不会**触发重新编译，跑起来的仍是上次编译进去的那一套，而且没有任何报错。

这不是推测，是实测出来的：

| 改动 | 无 `build.rs` | 有 `build.rs` |
| --- | --- | --- |
| 新增一条迁移 | 已应用数**纹丝不动**（静默忽略） | 1 → 2 |
| 删掉一条迁移 | — | 3 → 2 |
| 改一条迁移的内容 | — | 重编，新内容生效 |

「改一条迁移的内容」那一行值得单独看一眼：判据不能用"已应用条数"——增删能看出条数变化，
改内容看不出来。实测时是把每条迁移的 SQL 原文打出来，看到 `-- third A` 变成
`-- third B CHANGED` 才算证到，全程没有动任何 `.rs`。

## 命名

`<VERSION>_<DESCRIPTION>.sql`，版本号单调递增。

不符合这个格式的文件被**静默跳过**——这份 `README.md` 能放在这里就是靠这条规则（实测：
目录里有它时迁移集仍然是干净的一条）。别指望它会报错提醒你名字写错了。

## 纪律

- **只增不改。** 已经发布出去的迁移，内容一个字节都不能动：`_sqlx_migrations` 表里存着每条
  迁移的校验和，改了内容 = 校验和不符 = 下次启动直接失败。上面那张表里的"改内容"一行是
  为了证明 `build.rs` 有效，不是许可。
- **元数据异常一律 fail-fast。** 校验和不符 / 版本缺失 / 上次迁移中途挂掉留下的 dirty 记录，
  三种都不自动修复。自动修复意味着在没人看着的时候改数据库，那比启动失败危险得多。
- **模板自带的迁移集不建任何业务表。** 见下。

## 留给第一个要读"当前 schema 版本"的人

模板里**没有**这样的查询——`/v1/info` 给的是构建信息，没有任何端点暴露 schema 版本，门面上
也没有对应的方法。按"不预铺没有消费者的东西"，它不该先摆在这里。

但有一个坑值得先写下来，因为它只会在出事那天暴露：`_sqlx_migrations` 里**失败的迁移也有行**
（`success` 列为假）。取最大版本时必须带上过滤：

```text
SELECT MAX(version) FROM _sqlx_migrations WHERE success = TRUE
```

不带 `WHERE` 的话，一次半途失败的迁移会让进程对外**报出一个从未成功应用过的版本号**——而这
正是排障时最需要可信的那个数字。

## 为什么基线迁移是空的

`0001_baseline.sql` 只有注释。它存在的理由有三个：

1. 迁移这条路径必须在模板里就被真的走一遍——一条都没有的话，`open` 里的迁移分支从来没被
   执行过，第一个加迁移的人才会发现它坏了。
2. `_sqlx_migrations` 表因此在首次启动时就被建出来，"库是空的"与"库没初始化"不再是同一种状态。
3. 它给出了文件名格式的范例。

`storage` 有一条会**主动过期**的断言 `migration_set_creates_no_business_tables`：它直连原库
核对表清单，要求除 `_sqlx_migrations` 之外一张表都没有。第一条业务迁移落地时这条断言会红，
那时把它改成对应的期望值——红在这里比"模板自带的表悄悄进了生产库"好。
