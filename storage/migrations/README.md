# 迁移脚本

`sqlite/` 与 `postgres/` 分别存放两个后端的迁移脚本，各自独立编号但**成对新增**。
模板不带任何迁移（没有仓储就没有表）；目录先存在，是让 `sqlx::migrate!` 有地方看。

sqlx 只识别 `<VERSION>_<DESCRIPTION>.sql` 形式的文件，其余文件（包括各目录的
README）一律忽略，不会污染迁移集合。

## 命名

```text
<VERSION>_<DESCRIPTION>.sql
```

`VERSION` 用递增整数（如 `0001`），`DESCRIPTION` 用小写下划线短语。

## 取号：按消费者到场顺序，不预留

新迁移在**仓储实现真的要用它的那个提交里**取当时的下一个号，不预先钉一张
「里程碑 A 用 0004、B 用 0005……」的预留表。没有仓储实现要用的表不写迁移——
预留表等于替尚未存在的消费者先占一个号，改期或改形后表上就会出现一个永远不落地
的洞，读者分不清它是「还没来」还是「已经取消」。

并行的几条线因此**会撞号**，撞号按合并顺序解决：先合入主干的一方定号，后合的一方
rebase 时把自己的迁移改成新的下一个号。这一步便宜，正是因为迁移在合入之前从未被
任何环境执行过——而它一旦合入并发布，就受下面「已发布的迁移不可修改」约束。

## 规则

- **成对新增。** 一个业务用例同时提交 `sqlite/` 与 `postgres/` 两侧脚本，不允许只落一侧。
- **已发布的迁移不可修改。** 已经在任何环境执行过的脚本一律视为只读，sqlx 校验校验和，
  改动会导致启动失败。修正必须走新增脚本。
- **按真实消费者引入。** 没有仓储实现要用的表不写迁移。
- **每个文件第一屏写明自己归谁维护**（手写 / 由某注册表渲染），读者不该靠猜来决定能不能直接改。

## 新增文件为何需要 `build.rs`

`sqlx::migrate!` 为**已存在**的迁移文件生成 `include_str!`，修改这些文件能触发重编译；
但**新增**文件时，宏上一次的展开结果里没有该路径，cargo 认不出变化，于是跳过重编译——
新迁移不报错、不告警，只是静默不生效。`storage/build.rs` 因此声明了两个迁移目录的
`rerun-if-changed`。**不要删除该文件。**

## 已知限制：旧库不可直接复用

sqlx 在启动时会校验「数据库中已应用的迁移」是否都存在于当前迁移集合中，若数据库里
有本集合不认识的版本，会返回 `MigrateError::VersionMissing` 并中止启动。把别的程序的
数据库文件直接交给本程序会启动失败，这是预期行为。
